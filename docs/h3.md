# H3 clip composition (obvpm/h3)

Nodes for growing MiniMax H3 videos **non-linearly**: save every take
together with its latents, then extend it forward, prepend a lead-in,
bridge between two clips, and compose the result on a timeline — with
exact latent-grade continuation instead of lossy pixel round-trips.

For per-node details see the [node reference](h3-nodes.md). This page
covers the concepts, the standard workflows, the timeline widget, and
[upscaling and refining](#upscaling-and-refining) the finished cut.

**Requirements:** a ComfyUI from 2026-08-13 or later (the pack pins
through core's native MiniMax H3 keyframe anchoring; older cores are
refused with a clear message at apply time). No extra Python
dependencies. The refine workflow additionally uses a latent upscaler
for H3 (the example: Comfyui_Minimax_h3_latent_Upscaler, 3D node,
temporal chunking on).

## Concepts

### Takes and clip pairs

One queue run produces one **take**. A take is saved as a **clip
pair**: the delivered MP4 plus a `.mctx.safetensors` **sidecar** right
next to it, holding the take's full raw video + audio latents and a
metadata header. The MP4 is the delivery copy; the sidecar is the
master — any clip that has one can later seed a continuation with zero
generation loss.

Sidecars are not small (roughly 2–3 MB per second at 1280×704), but
they are what makes everything below possible. Delete a sidecar and its
MP4 remains a normal video; it just can't be continued at latent grade
anymore.

### The sidecar format (`mctx_v1`)

The header records:

- `self_id` — the SHA-256 of the paired MP4. Every load verifies this
  pairing; a video that was re-encoded, edited or swapped since the
  take was saved is refused for latent continuation (the pixel route
  still works).
- `parent_id`, `relation`, `parent_join_frame` — a fast-path summary of
  the lineage edge for simple cases (one parent).
- `pins` — the full generation recipe: exactly which windows of which
  source clips were pinned, and where. This is the authoritative
  lineage record and is multi-parent-native (a bridge take has two
  parents here).
- frame bookkeeping (`raw_frames`, `delivered_frames`,
  `pinned_head_frames`, `pinned_tail_frames`), resolution, fps.
- `user_meta` — one opaque JSON blob for your own provenance. Its
  `metadata` widget is hidden now that the prompt and the whole workflow
  are captured automatically; the field remains in the format.

Alongside the latents the sidecar also stores the **workflow that made
the clip**, the way core embeds one in a PNG:

- `workflow` — the UI graph, the thing you reopen and edit.
- `prompt` — the API-format graph, what actually ran.

These are kept as separate tensors rather than header entries, so a
sidecar can carry a large workflow without making header reads any more
expensive.

The **MP4 carries them too**, as container tags named `workflow` and
`prompt` — the same scheme core's Save Video uses, so dropping a take
onto the ComfyUI canvas loads the graph that made it, and a clip shared
without its sidecar still knows where it came from. Derived files do not
get them: seam bridges, full previews and exports are not takes.

`--disable-metadata` suppresses both copies; note that a workflow names
local paths, model files and often your username, which matters more for
the MP4, since that is the file you actually share.

Lineage is **content-addressed**: there is no registry or project
database. Finding a clip's parent means scanning sidecar headers for a
matching `self_id`, which is cheap because headers are read without
loading the tensors — and stays cheap no matter how big the embedded
workflow is.

The format name `mctx_v1` is deliberately unbranded — it is meant as an
open convention any H3 pack can read or write, not something owned by
this pack.

### Pins

A **pin** carries a window of a source clip's latents into the next
generation as fixed context:

- **before** placement — the pinned window opens the new clip; the
  generation continues *out of* it. This is **extend**.
- **after** placement — the pinned window closes the new clip; the
  generation runs *toward* it. This is **prepend**.
- **one of each** in the same run — the generation must depart one
  clip and arrive at another. This is **bridging**.

Pinned frames are *scaffolding*: they are re-rendered as part of the
take, then trimmed off before delivery, so the delivered clip contains
only newly generated content. The sidecar records how much was pinned
on each side, and every seam downstream (timeline, assembly) is derived
from that record.

Window sizes come from H3's context ladder: **5 / 22 / 39 / 56**
frames (22 is the everyday choice; longer windows pin more motion but
leave less room for new content; the 1-frame window is reserved for a
future keyframe path). Latent slices must start on H3's 17-frame group
grid — the convenience pin modes shift off-grid edges automatically and
log where the seam lands, while the explicit Pin Spec node refuses
misaligned cuts and names the nearest valid frames.

### The three wires

| Wire | Carried by | Contents |
|---|---|---|
| `OBVPM_H3_MCTX` | loaders → Pin Spec | one clip's verified latents + header (its identity rides the wire) |
| `OBVPM_H3_PINSPECS` | Pin Spec / loaders / Timeline → Apply | a list of pin *descriptions* — pure data, chainable like LoRA stacks |
| `OBVPM_H3_PINS` | Apply → Trim / Save | the *resolved* pins: what was actually sliced, authoritative for trim amounts and the sidecar recipe |

## Workflows

### Root take

Your normal MiniMax H3 workflow, ended with **H3 MCtx Trim and Save
Video** instead of a plain video save (wire the sampler's latent to
`samples`, the decoded images/audio, and leave `pins` unwired). The
clip is saved as a pair and recorded as a root.

You can leave an **H3 MCtx Apply Pins** node in the graph permanently:
with nothing wired to `pin_specs` it passes the conditioning through
untouched, so the same graph does root generation and continuation
depending on what feeds it.

### Extending a clip

```
H3 MCtx Load (create_pins: extend (pin tail))
    └─ pin_specs ─► H3 MCtx Apply Pins ─ conditioning ─► guider / sampler
                        ▲ latent: the SAME empty AV latent you feed the sampler
sampler ─► VAE decode ─► H3 MCtx Trim and Save Video
                             ▲ samples: sampler latent   ▲ pins: from Apply
```

1. **H3 MCtx Load** picks the clip and, with `create_pins` set to
   `extend (pin tail)`, emits a ready-made pin spec (no separate Pin
   Spec node needed).
2. **H3 MCtx Apply Pins** sits between your prompt conditioning and
   the sampler. It slices the pinned window and attaches it as native
   keyframe anchors. The `latent` input must be the same empty AV
   latent the sampler consumes — it is authoritative for length and
   resolution.
3. **H3 MCtx Trim and Save Video** takes the *untrimmed* decode plus
   the `pins` wire from Apply, removes the scaffolding, and saves the
   new clip pair with its lineage recorded.

The new clip plays seamlessly after its parent — assembly nodes derive
the exact join from the sidecars.

### Prepending (generating a lead-in)

Same graph with `create_pins` set to `prepend (pin head)`: the source's
head is pinned at the *end* of the new clip, and the generation runs
toward it.

Prepend seams are harder for the model than extend seams: the pinned
content is always reproduced exactly, but whether the generated motion
*converges* into it smoothly is seed-dependent. If the Result Preview
reports a hard cut, reroll the seed (typically one in a few converges);
more sampling steps and a longer window can also help.

### Extending footage that has no sidecar

An import, an old take, a clip whose `.mctx.safetensors` was deleted —
none of them have latents, so there is nothing to slice a pin out of.
The fallback is to encode their pixels:

```
H3 MCtx Load Video  (mctx output unused — it is None)
  ├─ images ─┐
  └─ audio ──┤
             ├─→ H3 MCtx From Frames  (+ vae, audio_vae, latent)
             │      keep: tail   max_frames: 22
             └─→ mctx → H3 MCtx Pin Spec → H3 MCtx Apply Pins → …
```

From there the graph is identical to a normal extend. Two things are
different, and both are permanent:

- **The join is pixel-grade, not exact.** A VAE round trip is lossy, so
  the pinned frames are a close reproduction rather than the same
  latents. Apply says so in the log.
- **The new take still records what it continues.** Its sidecar names the
  source file by content hash and path, with `parent_grade: pixel` to say
  the pinned content came through a VAE rather than off a sidecar. So the
  Result Preview shows the pair, the timeline draws the link and cuts at
  the right frame, and seam repair works — the *lineage* is exact even
  though the *content* is not.

  (Through the hand-built **H3 MCtx From Frames** route the take is a
  root instead: frames arrive on a wire that may have graded or cropped
  them, so there is nothing honest to hash. The timeline route decodes
  the file itself, which is what makes the claim true there.)

Set `keep` to `tail` for an extend and `head` for a prepend: footage is
cut to a legal clip length before encoding, and `keep` decides which end
loses the surplus frames. Set `max_frames` to your pin window — the VAE
cost is per frame, and a 22-frame pin only needs 22 frames.

A clip that *does* have a sidecar should never come this way. The
pixel route is a fallback, not a shortcut.

**Or just use the timeline.** Since 2026-08-20 the Timeline offers
extend / prepend on sidecar-less clips too: the toggles appear with a
**dashed** border (and seam-popup entries read "+ extend new (pixels)")
to mark that the join will be pixel-grade. Connect `vae` and `audio_vae`
on **H3 MCtx Apply Pins** once, and the timeline route works for imported
footage exactly like any other clip — no loader, no From Frames node.
Apply decodes only the pinned window from the file, so the cost is the
window, not the clip.

Imported clips get an identity of their own, too: the timeline asks the
server for a plain video's content hash and length, so it can be named as
a parent and joined to properly. Its bar still reads **no mctx** — there
are no latents in it to slice — but it is a first-class citizen of the
cut.

A timeline cut on a sidecar-less clip has one advantage over a
latent-grade one: **it is never refused for being off the 17-frame
grid**, and never silently shifted onto it either. The grid exists
because a latent slice must start at cycle phase 0; an encode defines
phase 0 wherever the window starts, so the cut you dragged is the cut you
get.

### Bridging (filling between two clips)

Chain two pins into one Apply: a tail/before pin from the clip you are
leaving and a head/after pin from the clip you are arriving at — either
two **H3 MCtx Pin Spec** nodes chained on the `OBVPM_H3_PINSPECS` wire, or (much
easier) a bridge pin set up in the Timeline widget. The free frames in
the middle are generated to connect the two. Seam convergence applies
on *both* ends, so expect to reroll seeds.

### Generating straight from the timeline

**H3 MCtx Timeline**'s `pin_specs` output makes the timeline itself the
source of the next run: click a seam or select a clip in the widget,
choose extend / prepend (or replace a middle clip, which pins both
sides as a bridge), and wire `pin_specs` to Apply. No loader node, no
MCTX wires — the clip is re-verified against its sidecar hash at run
time. With nothing pinned the output is empty and Apply passes through
(plain root generation).

## The Timeline widget

**H3 MCtx Timeline** is the composition hub. It is *not* an output
node: previewing and exporting are button-driven and never run in a
workflow, so queueing generations while composing costs nothing.

**The strip.** Each clip is a block showing its name, length and play
range, an `mctx` badge, and a remove ✕. Blocks are sized by played
frames. Drag blocks to reorder. The colored bars at a block's ends show
its link state: **green** = a real lineage link (the seam is derived
from the sidecars), **purple** = the side a pinned generation will
regenerate, gray = no link. A purple *extending* / *prepending* badge
marks the pinned clip.

**Seams.** Hover the gap between clips (or the outer edges of the
strip) and a pill appears; click it for the seam menu: insert an
existing clip on either side, replace a side while keeping the link, or
**+ extend new** / **+ prepend new** to aim the next generation at that
seam (click again to un-aim). A white **+** on a pill marks where the
next run will attach.

**Selected clip.** Clicking a block selects it; the bar below shows its
name and play range, with **prepend clip** / **extend clip** toggle
buttons. Toggling both sides of a middle clip — or replacing a clip
that is linked on both sides — pins a **bridge**.

**Next run bar.** Always visible below the strip: what the next
generation will do (`root generation (no pin)`, `extends <clip>`,
`bridges A → B`), with a window-size button (cycles 22/39/56) and a ✕
to clear the pin.

**Run mode.** An **upscale** toggle sits at the right end of the header,
past **export**: off (resting chrome) a Run generates, on (filled) a Run
refines. It picks which half of the workflow a Run is for, on the
Timeline's `upscaling` output; see *Switching branches* under
[H3 MCtx Timeline](h3-nodes.md#h3-mctx-timeline) for the graph side. Like
**snap cuts** it rides the toolbar rather than sitting among the node's
setup widgets, because it is a mode you flip while working (the
`upscaling` widget itself stays declared and hidden — `widgets_values` is
positional). Switched on, the strip stops advertising a generation it
will not do: the next-run bar reads **upscale — refine and render the cut**, the
*extending* / *prepending* badges and purple end bars come off, and the
controls that set a pin (the clip toggles, **+ extend new** /
**+ prepend new**, the bridge **+**) are withdrawn.

Withdrawn, not disabled, and nothing is cleared: the pin stays in
`pin_state` exactly as it was and the strip comes back as you left it
when you switch to `generation`. That is why the controls go away rather
than merely looking unarmed — an armed toggle drawn unarmed invites the
click that would clear the very pin this mode is keeping. Repairs, cuts,
reordering, preview and export are unaffected; they describe the cut,
which every mode still plays.

**Adding clips.** `+ add` in the header lists eligible clips in
`base_folder`; you can also **drag videos straight into the strip**
(from your file manager, or from an asset browser) — they land at the
gap under the cursor. Files already in the output folder are used in
place (sidecar intact); others are uploaded. Drops whose resolution
does not match the timeline are rejected before anything is copied.
The hidden sequence text behind the widget can be hand-edited via the
✎ button (one output-relative path per line, `# ` comments, ` @ N` to
force an entry frame).

**Zoom.** The strip keeps a persistent scale rather than fitting the
sequence to the widget, so blocks stop resizing every time you edit.
`+` / `−` zoom, `fit` sets the scale so the whole sequence fills the
width once (and then leaves it alone), and the ruler scrolls when the
content is wider than the widget. A bare **wheel over the ruler** zooms
— the ruler *is* the scale — and **ctrl+wheel over the strip** does the
same, anchored at the cursor.

**Cuts.** Drag a block's left or right edge to change where that clip
enters or exits. The handles snap to the 17-frame latent grid while
**snap cuts** is on (toolbar); turn it off to place a cut anywhere.
A cut clip shows its play range in the block, and a seam derived from
the sidecars turns into a *trim-point* seam — still green, still a real
link, just entering or exiting somewhere other than the clip's own edge.

**Gaps.** Ctrl+drag in empty space to open a gap between clips; drag its
edges to resize, and the strip draws it as a hatched block. A gap is a
piece of the timeline with nothing in it yet — so it is also the natural
place to **generate the clip that belongs there**: click the gap's seam
pill and the menu offers a bridge, pinning the clip on the left as an
extend and the clip on the right as a prepend in one run. The take that
comes back drops into the gap.

**Per-seam settings.** Seam repair is configured per join, not just per
node — click the **⚙** on a seam pill (or the cog in the Result
Preview) to open the settings for that one join. Anything you do not
set follows the node's own widgets; **Reset to timeline defaults**
clears the overrides again. See *Seam repair* below.

**After each run.** The Result Preview shows the finished take and
offers **+ add to timeline**; the Timeline places it at the position its
lineage implies. A new take that replaces a pinned seam *replaces* the
old clip in the sequence (the old file stays on disk). The Timeline does
not scan for new clips itself — one node reports a run, and it is the
one that already knows which run was its own.

**Preview and export.** `▶ quick` plays the sequence with chained
players (instant, near-gapless). `▶ full` asks the server to build the
real cut as a single file — built by smart-cut, so it is exact — and
plays that; the build is cached and survives reloads. The ruler above
the strip scrubs both modes. **export** copies the current full build
into the output folder under `export_filename_prefix` —
byte-identical to the preview you just watched.

## The Result Preview

Wire an H3 Save node's `path` output into **H3 MCtx Result Preview**.
After each run it shows the fresh take *in context*: beside its parent
(extend), its target (prepend), or between both (bridge), playable as
one seamless preview. Each seam wears a **measured verdict** — the
actual motion discontinuity at the join, rated `seamless` / `soft
bump` / `hard cut` — so you know whether to keep the take or reroll
before touching the timeline. Buttons: **+ add to timeline** (offered
when a Timeline node for that folder exists), **✕ delete** (removes
the MP4 with everything filed under its name -- sidecar and
conditioning cache), **dismiss**.

While the run is sampling, the same box shows the live preview from
KJNodes' Model Preview Override if one is on the sampler's model, so
that node can be collapsed out of the way.

## Assembling in-graph

**H3 MCtx Assemble** is the pipeline variant of the timeline: the same
sequence text, but it builds the cut when the workflow runs and outputs
`path` / `images` / `audio` for further processing. Writes by
**smart-cut**: video packets are stream-copied bit for bit wherever
possible and only sub-GOP frames around a mid-clip seam are re-encoded;
audio is encoded once as a continuous track. The source takes remain
the masters — assembly is delivery, not a take, and writes no sidecar.

## Upscaling and refining

The second half of the workflow, behind the timeline's **upscale**
toggle, turns a finished cut into a refined one at a higher resolution.
It refines the **whole timeline as one piece**, because refining clip
by clip cannot be seamless: a refine re-invents most of the fine
texture from its prior and its noise, and two clips refined separately
invent it differently on either side of the join, however exact the
hold between them.

The route, node by node in [the joint refine](h3-nodes.md#the-joint-refine):

1. **H3 Join Latents** reads the timeline's sequence and lays every
   clip's raw latent onto one long latent at its true position — a
   pinned clip on the very rows it was generated from, the cut deciding
   who owns each row where clips overlap.
2. A **latent upscaler** doubles it. Keep the upscaler's temporal
   chunking on (see below).
3. **H3 Joint Audio Mask** holds the audio, which needs no refining.
4. **H3 Joint Conditioning** packs each clip's own conditioning — the
   prompt and references it was generated with — so a timeline of
   several prompts stays several.
5. **H3 Context Windowing** on the model samples the long latent in
   clip-sized overlapping windows (5 s by default, overlapping 1.25 s),
   blending the predictions across each overlap at every step, each
   window under the conditioning of the clip that owns it. Every row is
   sampled with its neighbours in view and nothing is committed ahead of
   them; that is what removes the seams. Memory is one window's worth,
   and a two-line gauge shows the windows inside each sampler step.
6. **H3 Joint VAE Decode and Save** decodes the sampled latent a few seconds at a
   time, streams the frames into the encoder, and writes the finished
   cut as one MP4 — with a sidecar holding the refined latent and, when
   the joint conditioning is wired, a `.cond`, so the rendered cut is a
   take that can go back on a timeline and be refined again.

**Refine strength.** The sampler's BasicScheduler `denoise` sets where
the refine starts. It is a fraction of the schedule, and with H3's
timestep shift of 12 the noise level the model actually starts from is
12d/(1+11d): 0.2 starts at 75 % noise and is the working value; 0.075
starts at 49 %.

**The upscaler must chunk along time.** This is the one requirement
outside this pack. The H3 3D latent upscaler normalises over channels,
time, height and width together, and it was trained on short clips.
Handed a whole timeline in one pass, it normalises every frame against
the statistics of the entire video, its output drifts, and the refine
reads that drift as detail and hallucinates on it: hard white points on
sunlit hair, marks on a face, shimmering eyes, in places that change
with the noise seed. Leave the upscaler's `enable_temporal_chunking` on
and the same refine is clean. The full record of how this was found is
in [joint-refine-investigation.md](joint-refine-investigation.md).

## Seam repair

Even a perfectly-derived join can be *visible*, and the reason is
specific rather than mysterious.

An extend hands the model a latent slice of its parent; the model
re-renders that same window, then continues past it. Assembly keeps the
**parent's** pixels for the window and delivers the child from after it
-- so the join lands where the parent's rendering of a moment meets the
child's continuation of *its own* rendering of that same moment. The two
renderings do not agree on level, and that disagreement is what you see.

It is a bias, not noise. Measured over 38 parent-to-child joins in one
project: four independently sampled takes off the same clip opened
+3.78, +3.18, +3.38, +3.59 -- which is why re-rolling never fixed it. The
median step is 2.87 luma against a median frame-to-frame noise of 0.44,
about **6x anything else on screen**, and it self-corrects within roughly
the first 12 frames.

Three repairs address it, and they compose. All are on by default except
audio de-click, and every one can be overridden per join.

### Level lock

Matches the continuing clip's opening to where the parent was *heading*.
Per channel, over the first `level_lock_frames` frames (default **12**):
predict the parent's trajectory from a line through its last frames --
not simply its last frame, or a clip legitimately walking into shade gets
"corrected" back out of its own lighting change -- then ramp the child
back to its native grade by frame N.

The gain is **multiplicative**, so black stays black and midtones scale
the way exposure actually behaves; an offset would lift the blacks and
read as haze. Decaying to identity is what makes it safe to chain: every
clip is back at its own grade within half a second, so a fifty-clip chain
accumulates nothing.

- **`level_lock_flicker`** also straightens a *swing* -- opening frames
  that oscillate rather than sitting at a constant offset.
- **`level_lock_local`** matches per region instead of per frame. A
  whole-frame gain holds the average exactly while leaving regions
  several luma out, and that leftover pattern shifts frame to frame as
  visible local flicker.
- It corrects only when the step beats the local frame-to-frame noise by
  a clear margin, so a join that does not need it is left alone.

### Crossfade

Both renderings of the overlap exist -- the parent's in its delivered
frames, the child's in the `overlap` blob its sidecar carries. They cover
the **same moment**, so a fade between them is invisible as content and
turns the level step into a gradual handover. At the end of the fade the
picture is entirely the child's rendering, which is exactly what its
delivered frames continue from, so nothing is discontinuous afterwards.

Duration does not change: the overlap replaces the parent's tail frames
in place rather than being inserted.

`crossfade_frames` defaults to **0, meaning the whole overlap**. That is
deliberate -- the child's disagreement with its context is nearly as
large at the window's *start* as at its end (it grows only 1.26x across
it), so there is no short fade that hides the step. Fading over four
frames ramps a quarter of it and cuts the rest.

The fade is **equal-power**, and the two sources are level-matched
*before* fading. Without that the fade makes things worse rather than
better: the model's re-render starts at its conditioning's level and
drifts brighter across the window (measured 123.0 to 130.3 against a
parent sitting at 122), so an unmatched fade walks the picture up by 7
luma and the delivered frames then decay back down -- a brightness swell
in place of a step.

Crossfade does **not** fix flicker: the oscillation lives in the frames
*after* the overlap, where the model has left its conditioning behind,
and the fade ends exactly where that begins. Use level lock's swing
straightening for that. The two compose, and both run by default.

### Audio de-click

For joins a crossfade does not cover, a 5 ms taper each side removes the
sample-edge click without leaving an audible hole. Not the 15 ms an
overlapping crossfade uses: a crossfade *sums* two runs so its length
costs nothing audibly, while this has no second run to fade into and dips
to silence. A 30 ms hole in sustained ambience is a soft blip -- one
artefact traded for another. 10 ms total sits under the threshold at
which the ear hears a gap, and is still far longer than the single sample
that causes the click.

Off by default, because it is the exact complement of crossfade: it is
for the boundaries the fade does not reach.

### What is available where

The dialog hides what cannot act on the join in front of you, rather than
offering a promise the build will not keep:

| repair | needs |
|---|---|
| level lock | a real `extends` link |
| crossfade | that, **and** the join at its natural place (neither side cut), **and** a stored overlap in the child's sidecar |
| audio de-click | a join no crossfade covers -- the exact complement |

So a butt join between unrelated clips offers only de-click, and a
trim-point join offers level lock but not crossfade: cut either side and
the overlap is no longer where the join now is, so fading there would
blend two different moments.

### Setting them

Node-wide on the Timeline's widgets; per join via the **cog** on a seam
pill or in the Result Preview. Overrides live in the sequence line
itself, on the clip to the right of the join:

```
clip_00042.mp4 @ 12..250 [level_lock_frames=18 crossfade=off]
```

which is why they survive reorders, edits and hand-editing -- there is no
side table of join indices to fall out of step with the cut. **Reset to
timeline defaults** clears a join's overrides so it follows the node
again.

## Seam quality and diagnostics

Two different things are shown in two different places, deliberately:

- **Timeline colors are geometry.** Green means "a real lineage link —
  the cut point is derived from the sidecars." It says nothing about
  how the motion looks.
- **Result Preview verdicts are measurement.** The ratio of the
  motion step across the seam to the clip's typical motion step,
  computed from the latents (`< 1.2` seamless, `< 1.8` soft bump, else
  hard cut).

The same measurement is available in bulk from the command line:

```
python seam_report.py <folder-with-clips>
```

prints per-clip **fidelity** (how exactly the pinned window reproduced
its source — ~0.99+ means conditioning was obeyed) and the **seam
ratio** at the generated↔pinned boundary.

## The sequence line

The timeline widget is a view over a plain text sequence -- one entry per
line, editable by hand behind the pencil button. Everything the strip can
express is expressible here, which is what makes a composition
inspectable and diffable rather than opaque.

```
clip_00007.mp4                          a whole clip
clip_00012.mp4 @ 22                     enters at frame 22
clip_00012.mp4 @ ..250                  exits at frame 250
clip_00012.mp4 @ 22..250                both
~ 40                                    a 40-frame gap
# a line starting with a hash is a comment
clip_00019.mp4 [crossfade=off]          per-seam override
clip_00019.mp4 @ 22..250 [level_lock_frames=18 crossfade=off]
```

- Paths are **output-relative**, the same values the loaders list.
- `@ enter..exit` are **delivered** frames of that clip.
- `~ N` is a gap of N frames -- empty timeline, and the place a bridge
  generation lands.
- `[...]` carries per-seam settings for the join on that clip's **left**;
  see *Seam repair*. Unset keys follow the node's own widgets.

The seven settings are `level_lock`, `level_lock_frames`,
`level_lock_flicker`, `level_lock_local`, `crossfade`, `crossfade_frames`
and `audio_declick`. Booleans read `on`/`off` (also `1`/`0`,
`true`/`false`, `yes`/`no`) and are written back as `on`/`off`. An
unknown key is ignored rather than fatal -- a wrong *setting* degrades to
the timeline default, whereas a wrong *entry* would drop content, which
is why a malformed `~` gap fails loudly and this does not.

## Limits worth knowing

- H3 is 24 fps, and raw take lengths sit on a `17k + 5` frame grid
  (5..3592). Delivered length = raw − pinned scaffolding.
- Every clip in a continuation chain must share one resolution:
  latents cannot be resized. Mismatches are refused loudly (and
  mismatched drops on the timeline are rejected up front).
- Latent-grade cuts land on the 17-frame group grid; convenience pins
  auto-shift, the explicit Pin Spec refuses and suggests.
- H3 delivers ~8 ms more audio than video per clip; the trim nodes
  truncate audio to exactly `frames/fps` so the error cannot compound
  across a chain.
- `place: at_frame` (interior pins / repaint) is declared on the Pin
  Spec node but not implemented yet; Apply refuses it with a pointer.
- Footage with no sidecar can still be extended — from the timeline
  directly, or through **H3 MCtx From Frames** in a hand-built graph —
  but only at pixel grade. The timeline route needs `vae`/`audio_vae` on
  Apply, and records `parent_grade: pixel` on the take; the hand-built
  route produces a root, because an IMAGE wire carries nothing to hash.
- The 17-frame cut-grid rule applies to LATENT pins only. Pixel-route
  pins accept any cut frame.
- The joint refine needs the latent upscaler's temporal chunking **on**.
  Upscaling the whole timeline in one pass produces a prior the refine
  hallucinates on, at every strength and under every sampling scheme.
